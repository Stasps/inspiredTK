# О чем документ
Здесь описана структура состояния сервера (аналог сейв-файла для многопользовательской игры): снимки состояния симуляции.
Формат снапшотов - JSON. Оперативное хранение - реляционное (предварительно PostgreSQL, см. архитектурный документ). Это два физических представления одной логической модели: схема БД и JSON-снаппшот описывают одни и те же сущности и должны изменяться синхронно.

Нейронки могут изменять структуру только после ревью и аппрува от человека.

## Обязательные правила формата

- **version** - поле версии формата в шапке каждого снапшота. Обязательно с первой версии. Механика миграций между версиями - открытый вопрос, отсутствие поля - нет
- **Метаданные снапшота**: серверный таймстамп снятия (`snapshot_at`), версия формата (`version`), идентификатор последнего применённого события (`last_event_id`). Номер тика отсутствует — в архитектуре нет тика как такового (ленивые вычисления + планировщик событий). `last_event_id` связывает снапшот с журналом событий: восстановление = снапшот + все события с `id > last_event_id`.
- **Только целые числа или десятичные строки фиксированной точности** для всех количественных значений (ресурсы, провиант, курсы маркета, время). Никаких float: сериализация и арифметика float недетерминированы на уровне реализации, а симуляция обязана быть детерминированной. Ресурсы - в мелких единицах (например, ×1000 базовой единицы)
- **Серверное время** - единственное игровое время; в состоянии хранятся серверные таймстампы
- **Ленивые вычисления в состоянии**: для каждой сущности, генерирующей ресурсы (village, npc camp), в снапшоте хранятся `last_update_at` (серверный таймстамп последнего пересчёта) и текущие количества ресурсов. При чтении состояние «догоняется» формулой `rate * (now - last_update_at)`. В снапшоте НЕ хранятся предвычисленные «будущие» значения — только точка отсчёта и текущий срез.
- **События планировщика в состоянии**: активные дедлайны (завершение стройки, прибытие марша, окончание найма) хранятся как явные записи с серверным таймстампом срабатывания. Планировщик при старте восстанавливает min-heap из этих записей.

## Верхнеуровневые сущности (черновик, ждёт проектирования)

- **player**: аккаунт, герой, настройки (боевые окна)
- **village**: здания и уровни, склады (две категории - продовольственный/непродовольственный, зафиксировано в [[game-design]], «Склады»), войска, **`last_update_at`** (точка отсчёта ленивого пересчёта ресурсов)
- **map cell**: координаты, месторождения, занятость
- **npc camp/village**: лагеря и деревни варваров, рост, **`last_update_at`**
- **march**: движущиеся войска (отправление, прибытие, провиант), **`arrive_at`** (серверный таймстамп прибытия — дедлайн для планировщика)
- **scheduled event**: запись планировщика — `event_id`, `entity_type`, `entity_id`, `kind` (build_finish / march_arrive / hire_finish / …), `fire_at` (серверный таймстамп), `payload` (JSONB). Источник истины для восстановления min-heap планировщика после краша.
- **market rates**: курсы NPC-маркетмейкера
- **kingdom**: королевство, сокровищница, дипломатия (позже)
- **event log**: append-only журнал критичных событий (бои, транзакции, дипломатические действия). Каждая запись: `event_id` (монотонный), `at` (серверный таймстамп), `kind`, `entity_ref`, `payload` (JSONB), `idempotency_key` (уникальный ключ для защиты от дублей). Связь со снапшотом: `snapshot.last_event_id` → восстановление = снапшот + события с `id > last_event_id`. Повторное применение события с тем же `idempotency_key` не меняет состояние.

## Открытые вопросы

- Схема БД vs JSON-снаппшоты: что храним реляционно, что документами (граница между двумя представлениями одной модели, не два конкурирующих варианта). Гипотеза: «горячие» сущности (player, village, march, scheduled event) — реляционно; конфиги и редкие сущности — JSONB
- Версионирование формата состояния (миграции между версиями) - механика, поле version при этом обязательно уже сейчас
- Что входит в снимок сезона и как фиксируется его результат
- Что входит в переподключенческий снапшот игрока: полный мир невозможен, нужно определить видимую область (правило из сетевых правил архитектурного документа: снапшот + дельта за время обрыва). Дельта при переподключении = события из event log с `id > last_seen_event_id` клиента, отфильтрованные по видимой области
- Состав event log: какие события критичны и не восстановимы из состояния, а какие выводимы. Критерий: если событие нельзя вывести из текущего состояния + `last_update_at` — оно пишется в журнал
- **Политика снапшотов при ленивых вычислениях**: как часто снимать снапшот «грязного» актора (стартовое предложение: 5–10 минут), и как при восстановлении корректно «догнать» ресурсы от `last_update_at` снапшота до момента краша (формула от прошедшего времени, а не реплей каждого тика)
- **Восстановление планировщика**: при старте min-heap строится из таблицы `scheduled_event`; открытый вопрос — как обрабатывать события, чьё `fire_at` прошло во время простоя сервера (пакетная обработка в порядке `fire_at`)
