# О чем документ
Здесь описана техническая архитектура игры. Нужно ей следовать.

## Ключевое отличие от одиночной игры
Игра многопользовательская: **сервер авторитетен**. Клиент - тонкий: только отображение состояния и отправка команд. Вся экономика, бой и время считаются на сервере.

## Принятые решения

- **Язык бэкенда**: Go [Зафиксировано]. Сравнение с альтернативами (Rust, C#/.NET, Elixir) проведено, глубокий ресёрч альтернатив не требуется - выбор обоснован профилем нагрузки (событийная симуляция без тика: редкие команды и события планировщика, много idle-соединений, дешёвые горутины под сессии; скорость разработки важнее экстремальной производительности на ядро)
- **Форма сервера**: один процесс-монолит со слоями внутри. НЕ микросервисы на старте. Шардирование - горизонтальное решение на будущее, когда один процесс перестанет хватать, а не архитектурная основа
- **Транспорт клиент-сервер**: WebSocket [Рекомендация]. HTTP polling не подходит: это игра с постоянным соединением и серверными пушами (атаки, завершение строительства). Polling даст задержки и лишнюю нагрузку. Окончательно зафиксировать при первом прототипе клиента
- **Модель времени и конкурентности** [Зафиксировано]: событийная симуляция без тика. Ленивые вычисления ресурсов (Compute on Read) + планировщик событий (min-heap) внутри единственного актора симуляции; просроченные события проверяются по таймеру ближайшего события, без периодического опроса. Сетевой край - акторы-сессии игроков, рассылка адресная. Целевая нагрузка: 100 онлайн стабильно, 1000 в пике. Подробности - в разделе «Конкурентная модель»
- **Источник игрового баланса**: механики, цифры и формулы - из Travian Kingdoms как отправная точка (в дальнейшем баланс будет меняться). Игра собственная, вдохновлена геймплеем Travian Kingdoms, а не клон. `ref-balance/` (таблицы зданий и войск из Travian Legends / TravianZ 3.6, отличаются от Kingdoms) - дополнительный справочный материал, не ориентир; актуальную справку по Kingdoms ищем отдельным заданием. Реализация на Go — полностью авторская. Код PHP не копируется. Фракции и визуал — собственные.

## Архитектурные принципы

### Разделение transport / domain / storage
Ядро игры (домен: экономика, бой, карта, очереди) **не зависит от транспорта и БД**. HTTP/WebSocket-обработчики и SQL-код - тонкие адаптеры на краях. Это позволит потом менять клиент (мобильный), транспорт и БД без переписывания логики.

```
Client (View) → Transport (WebSocket/HTTP) → Domain (Game Logic) → Storage (SQL)
                    ↑ конфиги (Data) · сервисные utils (логи, метрики) - подключаются к слоям сбоку
```

### Единый источник времени
Серверное время - единственное игровое время. Клиентские таймстампы только для отображения и не влияют на расчёты. Синхронизация часов сервера (NTP) - часть деплоя.

### Детерминизм и версионируемость
- Боевая математика и формулы - детерминированные и покрыты тестами: одинаковый ввод → одинаковый результат на любом сервере и при любом переподключении
- Схема состояния версионируется с миграциями: ранний формат сейва не должен блокировать баланс-патч раунда

## Описание архитектуры
Data-Driven Layered Architecture, сервер-авторитетная.

Архитектура состоит из слоёв:

- **Data** - конфиги и статичные данные: ресурсы, здания, юниты, формулы боя, цены. Версионируемые файлы, валидация при старте
- **Game Logic** - серверная симуляция: **событийно-ориентированная с ленивыми вычислениями**. Ресурсы не тикают: вычисляются по формуле `rate * (now - last_update)` в момент чтения состояния. «Жёсткие» события (завершение стройки, прибытие марша, окончание найма) ставятся в планировщик и обрабатываются при наступлении серверного времени. Тик как таковой отсутствует.
- **Transport/API** - команды клиента: принимает, валидирует, передаёт в логику. WebSocket-обработчики не содержат игровых расчётов
- **View** - браузерный клиент, 2D. Читает состояние, отправляет команды через API
- **Storage** - хранение состояния симуляции (игроки, поселения, карта, марши, рынок). Схема состояния - в [[save-structure]]. Прямые SQL-запросы через pgx/sqlc, без тяжёлого ORM
- **Utils** - логи, метрики, аналитика

## Опасные места (проверять код-ревью)

- **Глобальный мьютекс на мир игры** - запрещён как архитектурный костыль. Конкурентный доступ к состоянию - через актор-модель: у состояния один владелец-горутина с почтовым ящиком (сейчас это актор симуляции, см. «Конкурентная модель»); шардирование по игрокам - следующий шаг, если замер покажет необходимость. Если «временно» захочется один `sync.Mutex` на всё - это сигнал пересмотреть модель состояния, а не писать мьютекс
- **Тяжёлый ORM** - запрещён в горячем пути (обработка событий, бой, марши, ленивый пересчёт ресурсов): N+1 запросы убьют производительность. Только прямые запросы/заранее сгенерированный код (sqlc)
- **Игровая логика внутри обработчиков соединений** - запрещено: WS-обработчик принимает команду и кладёт её в очередь актора симуляции; расчёт происходит в горутине симуляции при разборе очереди, а не в горутине соединения. Ответ на команду уходит только отправителю

## НЕЛЬЗЯ

- Хардкодить контент. Вместо этого под каждый вид сущности своя структура конфигов (единая структура на всех сущностей одного вида)
- Доверять клиенту: любые расчёты ресурсов, боя, времени - только на сервере
- Бесконтрольно создавать новые системы, которые дублируют уже существующие

## Сетевые правила

- Все игровые действия идемпотентны или валидируются против реплея: повтор команды клиента не должен дублировать ресурсы или войска
- Соединение (WebSocket) эфемерно: переподключение получает полное состояние, а не инкрементальные патчи
- Событийная шина разрешена и ожидается: атаки, строительство, торговля, уведомления - события. Шина - внутри процесса (каналы Go), не внешний брокер на старте
- Полное состояние при подключении - снапшот + дельта за время обрыва, а не пересчёт всей истории

## Открытые вопросы

- **Моменты пересчёта** (производство, бой, рынок): зафиксировать в [[save-structure]] или отдельном доке. Сама модель времени решена, см. «Принятые решения»
- **БД**: предварительно PostgreSQL (надёжность, JSONB для конфиг-состояния, зрелость экосистемы Go). Финальное решение - с первым прототипом нагрузки
- **Деплой**: где живёт сервер
- **Частота снапшотов состояния**: баланс между потерей прогресса при краше и нагрузкой на запись

## Конкурентная модель

- **Актор симуляции**: одна горутина владеет всем игровым состоянием и планировщиком. Все мутации идут последовательно в ней; ввод-вывод (сокеты, БД, сериализация JSON) в ней запрещён
- **Планировщик**: min-heap по `(fire_at, seq)` внутри актора симуляции, таймер на ближайшее событие, тикера нет. Обработчик получает `fire_at` как игровое время, поэтому опоздание обработки не сдвигает цепочки. Перед командой применяются все события с `fire_at <= now`. Отменённое событие из кучи не удаляется: обработчик сверяет его id с сущностью и отбрасывает устаревшее. Периодика (атаки мародёров, обновление курса рынка) - самоперепланирующиеся события. После простоя сервера куча разбирается в том же порядке до приёма соединений
- **Акторы-сессии игроков**: горутины чтения и записи на каждое подключение. Держат соединение, лимит частоты команд, `cmd_id`, исходящую очередь и подписки на карту. Игрового состояния не держат
- **Игрок в симуляции**: корень владения (свои поселения и марши), адрес рассылки и шов для будущего шардирования
- **Поселение и марш - данные, не акторы**: поселение принадлежит игроку; марш - значение с одним событием прибытия (войска и провиант списаны при отправке, прибытие меняет только цель и порождает обратный марш новым событием)
- **Писатель журнала и снапшотов**: отдельная горутина; симуляция в БД не ходит
- **Рассылка состояния**: адресная, broadcast всем запрещён. Обработчик помечает затронутых игроков (владелец поселения, владелец марша, защитник); после обработки каждый помеченный онлайн-игрок получает только своё состояние. Ежесекундной рассылки нет: клиент получает `{amount, rate, cap, as_of}` и `finish_at` и интерполирует сам по серверному времени. Ответ на команду (ack или ошибка с `cmd_id`) - только отправителю. Карта - по запросу области; подписка на участки карты - следующий этап
- **Очереди и переполнение** (значения стартовые, уточняются нагрузочным тестом):
  - команды одного игрока: token bucket, 10/с; при превышении отказ `rate_limited`, при повторах разрыв
  - общая очередь симуляции: 1024-2048, не больше 4 команд одного игрока в очереди; при переполнении отказ `server_busy` отправителю без блокировки, повтор безопасен благодаря `cmd_id`
  - исходящее состояние игрока: слот на 1, новое затирает старое
  - исходящие уведомления: около 64, таймаут записи 5-10 с; при переполнении разрыв соединения, при входе игрок получает полное состояние
  - журнал событий: ограниченный канал; при заполнении симуляция ждёт, терять записи нельзя
  - куча планировщика: ограничена правилами игры; метрика отставания, тревога при отставании больше 1 с
- **Запрет на глобальный мьютекс** остаётся: состояние защищено единственным владельцем, а не блокировкой. Любой `sync.Mutex` на «весь мир» - сигнал о неверной декомпозиции
- **Шардирование**: не делаем, пока замер не покажет необходимость (ядро симуляции занято больше 50% или планировщик отстаёт больше 1 с при 1000 онлайн). Тогда - акторы игроков со своим состоянием; шов уже есть, это владение по игрокам

## Персистентность

- **Снапшоты**: периодический дамп состояния акторов (игроки, поселения, активные марши) в PostgreSQL. Частота — открытый вопрос (стартовое предложение: 5–10 минут для «грязных» акторов).
- **Журнал событий**: критические транзакции (создание юнитов, бои, торговля) пишутся в append-only журнал (таблица `event_log` или WAL PostgreSQL). Восстановление после краша = последний снапшот + реплей событий с момента снапшота.
- **Идемпотентность реплея**: каждое событие имеет уникальный ID; повторное применение не меняет состояние.
