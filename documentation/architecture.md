# О чем документ
Здесь описана техническая архитектура игры. Нужно ей следовать.

## Ключевое отличие от одиночной игры
Игра многопользовательская: **сервер авторитетен**. Клиент - тонкий: только отображение состояния и отправка команд. Вся экономика, бой и время считаются на сервере.

## Принятые решения

- **Язык бэкенда**: Go [Зафиксировано]. Сравнение с альтернативами (Rust, C#/.NET, Elixir) проведено, глубокий ресёрч альтернатив не требуется - выбор обоснован профилем нагрузки (тиковая логика, много idle-соединений, скорость разработки важнее экстремальной производительности на ядро)
- **Форма сервера**: один процесс-монолит со слоями внутри. НЕ микросервисы на старте. Шардирование - горизонтальное решение на будущее, когда один процесс перестанет хватать, а не архитектурная основа
- **Транспорт клиент-сервер**: WebSocket [Рекомендация]. HTTP polling не подходит: это игра с постоянным соединением и серверными пушами (атаки, завершение строительства). Polling даст задержки и лишнюю нагрузку. Окончательно зафиксировать при первом прототипе клиента
- **Источник игрового баланса**: цифры и формулы берутся из TravianZ (T3.6) как справочный материал. Реализация на Go — полностью авторская. Код PHP не копируется. Фракции и визуал — собственные.

## Архитектурные принципы

### Разделение transport / domain / storage
Ядро игры (домен: экономика, бой, карта, очереди) **не зависит от транспорта и БД**. HTTP/WebSocket-обработчики и SQL-код - тонкие адаптеры на краях. Это позволит потом менять клиент (мобильный), транспорт и БД без переписывания логики.

```
Client (View) → Transport (WebSocket/HTTP) → Domain (Game Logic) → Storage (SQL)
                    ↑ конфиги (Data) · сервисные utils (логи, метрики) - подключаются к слоям сбоку
```

### Единый источник времени
Серверное время - единственное игровое время. Клиентские таймстампы только для отображения и не влияют на расчёты. Синхронизация часов сервера (NTP) - часть деплоя.

### Детерминизм и версионируемость
- Боевая математика и формулы - детерминированные и покрыты тестами: одинаковый ввод → одинаковый результат на любом сервере и при любом переподключении
- Схема состояния версионируется с миграциями: ранний формат сейва не должен блокировать баланс-патч раунда

## Описание архитектуры
Data-Driven Layered Architecture, сервер-авторитетная.

Архитектура состоит из слоёв:

- **Data** - конфиги и статичные данные: ресурсы, здания, юниты, формулы боя, цены. Версионируемые файлы, валидация при старте
- **Game Logic** - серверная симуляция: **событийно-ориентированная с ленивыми вычислениями**. Ресурсы не тикают: вычисляются по формуле `rate * (now - last_update)` в момент чтения состояния. «Жёсткие» события (завершение стройки, прибытие марша, окончание найма) ставятся в планировщик и обрабатываются при наступлении серверного времени. Тик как таковой отсутствует.
- **Transport/API** - команды клиента: принимает, валидирует, передаёт в логику. WebSocket-обработчики не содержат игровых расчётов
- **View** - браузерный клиент, 2D. Читает состояние, отправляет команды через API
- **Storage** - хранение состояния симуляции (игроки, деревни, карта, марши, рынок). Схема состояния - в [[save-structure]]. Прямые SQL-запросы через pgx/sqlc, без тяжёлого ORM
- **Utils** - логи, метрики, аналитика

## Опасные места (проверять код-ревью)

- **Глобальный мьютекс на мир игры** - запрещён как архитектурный костыль. Конкурентный доступ к состоянию - через шардирование (ячеек карты, игроков, городов) либо актор-модель: одна сущность - одна горутина с почтовым ящиком. Если «временно» захочется один `sync.Mutex` на всё - это сигнал пересмотреть модель состояния, а не писать мьютекс
- **Тяжёлый ORM** - запрещён в горячем пути (обработка событий, бой, марши, ленивый пересчёт ресурсов): N+1 запросы убьют производительность. Только прямые запросы/заранее сгенерированный код (sqlc)
- **Игровая логика внутри обработчиков соединений** - запрещено: WS-обработчик принимает команду и кладёт её в очередь домена, расчёт происходит в тике, а не в момент получения пакета

## НЕЛЬЗЯ

- Хардкодить контент. Вместо этого под каждый вид сущности своя структура конфигов (единая структура на всех сущностей одного вида)
- Доверять клиенту: любые расчёты ресурсов, боя, времени - только на сервере
- Бесконтрольно создавать новые системы, которые дублируют уже существующие

## Сетевые правила

- Все игровые действия идемпотентны или валидируются против реплея: повтор команды клиента не должен дублировать ресурсы или войска
- Соединение (WebSocket) эфемерно: переподключение получает полное состояние, а не инкрементальные патчи
- Событийная шина разрешена и ожидается: атаки, строительство, торговля, уведомления - события. Шина - внутри процесса (каналы Go), не внешний брокер на старте
- Полное состояние при подключении - снапшот + дельта за время обрыва, а не пересчёт всей истории

## Открытые вопросы

- **Модель времени**: ленивые вычисления ресурсов (Compute on Read) + планировщик событий (Scheduler) для «жёстких» дедлайнов. Периодический тик отсутствует. Моменты пересчёта (производство, бой, рынок) зафиксировать в [[save-structure]] или отдельном доке. Открытый вопрос: как часто запускать проверку просроченных событий (например, раз в 500 мс или по таймеру ближайшего события).
- **БД**: предварительно PostgreSQL (надёжность, JSONB для конфиг-состояния, зрелость экосистемы Go). Финальное решение - с первым прототипом нагрузки
- **Деплой**: где живёт сервер
- **Частота снапшотов состояния**: баланс между потерей прогресса при краше и нагрузкой на запись

## Конкурентная модель

- **Actor-модель**: одна сущность (игрок, деревня, марш) — одна горутина с почтовым ящиком (канал). Все мутации состояния сущности происходят последовательно внутри её горутины.
- **Запрет на глобальный мьютекс**: любой `sync.Mutex` на «весь мир» — сигнал о неверной декомпозиции.
- **Шардирование**: на старте — по игрокам (акторы игроков). При росте — по ячейкам карты.
- **Планировщик**: отдельная горутина (или пул) читает ближайшие события из приоритетной очереди (min-heap по времени) и рассылает сообщения соответствующим акторам.

## Персистентность

- **Снапшоты**: периодический дамп состояния акторов (игроки, деревни, активные марши) в PostgreSQL. Частота — открытый вопрос (стартовое предложение: 5–10 минут для «грязных» акторов).
- **Журнал событий**: критические транзакции (создание юнитов, бои, торговля) пишутся в append-only журнал (таблица `event_log` или WAL PostgreSQL). Восстановление после краша = последний снапшот + реплей событий с момента снапшота.
- **Идемпотентность реплея**: каждое событие имеет уникальный ID; повторное применение не меняет состояние.
