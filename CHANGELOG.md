# Changelog

## [0.1.2] - 2026-11-24
**Изменено**:
- ошибки команд и ответ на «Карту» получает только тот, кто отправил команду; другие игроки их больше не видят
- частые команды ограничены: не больше 10 в секунду на игрока (на все его вкладки вместе), лишние получают отказ, а после 20 отказов подряд соединение рвётся
- клиент, который перестал читать сокет, отключается: через 10 с ожидания записи или при 64 неотправленных уведомлениях; при входе он получит полное состояние
- в логе клиента ошибки показаны с кодом, например `[rate_limited]`
- повтор команды с тем же `cmd_id` (например, после обрыва связи) не выполняет её второй раз, а возвращает прежний ответ
- слишком большое входящее сообщение (больше 16 КиБ) рвёт соединение
- «зависшее» соединение (клиент пропал без закрытия, например отключили сеть) закрывается примерно через минуту: сервер шлёт ping раз в 30 с, а при тишине дольше 70 с рвёт сессию

**Технические детали**:
- протокол: команда `{type:"command", cmd, cmd_id, data}`, `cmd_id` обязателен (до 64 символов); ответы `{type:"ack", cmd_id}`, `{type:"error", cmd_id, data:{code, error}}`, `{type:"map", cmd_id, data}`
- коды ошибок: `bad_request`, `command_failed`, `rate_limited`, `server_busy`, `join_failed`
- `transport.Limits` / `DefaultLimits()`: общая очередь событий 1024, token bucket 10/с с запасом 10, не больше 10 команд игрока в очереди, 20 отказов подряд до разрыва, 64 уведомления, таймаут записи 10 с
- лимит частоты применяется к каждому входящему сообщению, включая неразборные; цикл симуляции вызывает `Event.Taken()` для каждой вынутой команды, это освобождает место игрока в очереди
- `Session.SendState` - слот на одно состояние с затиранием; `Session.Send` - очередь уведомлений; уведомления пишутся раньше состояния; `Hub.Send` и `Hub.BroadcastPerPlayer` кладут `state` в слот
- `Hub.Broadcast` удалён: рассылка всем запрещена
- дедупликация `cmd_id` (`transport/replies.go`): сервер помнит последние 64 `cmd_id` игрока (`Limits.ReplyMemory`) с ответом целиком; повтор выполненной команды получает сохранённый ответ, повтор идущей присоединяется к ожиданию, и ответ приходит всем приславшим сессиям. Память у игрока, а не у сессии: переживает переподключение, живёт до перезапуска процесса, в снапшот не пишется
- запоминаются только команды, дошедшие до симуляции; отказы `rate_limited`, `server_busy`, `bad_request` не запоминаются, повтор с тем же `cmd_id` выполнит команду. Ответ `get_map` не запоминается (только чтение, большой ответ), повтор выполняет её заново
- цикл симуляции отвечает через `Event.Reply(data, remember)` вместо `Session.Send`
- `transport.MaxMessageSize` = 16 КиБ: `conn.SetReadLimit` ставится при подключении в `HandleWebSocket`; превышение даёт ошибку чтения и закрытие сессии
- ping/pong: `Limits.PingInterval` = 30 с, `Limits.ReadTimeout` = 70 с; ping шлёт `Session.writeLoop` (единственный писатель), read deadline ставится при создании сессии и отодвигается на каждый pong и каждое принятое сообщение (`Session.extendRead`); интерфейс `wsConn` расширен `SetReadDeadline` и `SetPongHandler`; ответ pong даёт сама библиотека браузера, клиентский код не менялся
- нагрузочный замер залпа (1.2a3, `TestSalvoServerBusy`): при 4 местах игрока в очереди залп из 5 команд давал `server_busy` даже на свободном сервере (горутина чтения принимает команды быстрее, чем цикл симуляции их вынимает), залп из 10 - 5-6 отказов. `Limits.MaxQueuedPerPlayer` поднят с 4 до 10 (не меньше `CommandBurst`): залп в пределах запаса token bucket проходит целиком, сверх запаса отказывает `rate_limited`; `server_busy` остаётся защитой от переполнения общей очереди
- клиент: `cmd_id` = случайная приставка на загрузку страницы + счётчик, чтобы после перезагрузки страницы id не совпадали с запомненными

## [0.1.1] - 2026-11-24
**Добавлено**:
- несколько игроков на одном сервере: игрок задаётся в адресе клиента `index.html?player=alice` (без параметра - `debug`), в debug-режиме незнакомый игрок создаётся со своим поселением на ближайшей к центру свободной клетке
- в шапке клиента показан игрок, на карте своё поселение выделено рамкой

**Изменено**:
- команды выполняются от игрока соединения, а не от зашитого debug-игрока; команда на чужое поселение отклоняется
- медленный клиент больше не тормозит симуляцию: у каждого соединения свои горутины чтения и записи

**Технические детали**:
- `transport.Session`: горутина записи - единственный писатель в сокет; `Send` не блокирует, при переполнении исходящей очереди (`OutboxSize` = 32, временно до пределов из architecture.md) соединение закрывается
- `transport.Server.Events()`: события `EventJoin`, `EventCommand`, `EventLeave` для цикла симуляции; реестр сессий `transport.Hub` принадлежит циклу симуляции, без мьютекса
- подключение `ws://localhost:8080/ws?player=<id>`, id по маске `[a-z0-9_-]{1,32}`, иначе HTTP 400; без debugMode входит только существующий игрок
- первое сообщение сессии `hello`: `{playerId, name, settlements: [{id, x, y}], serverTimeUnix}`, затем состояние
- команды `upgrade_building`, `train_unit`, `add_resources`, `finish_now` требуют `settlementId`; `Engine.UpgradeBuilding`, `TrainUnits`, `AddResources` принимают `playerID` и проверяют владение
- рассылка раз в секунду теперь собирает состояние на каждого игрока (`Hub.BroadcastPerPlayer`); ошибки команд и ответ `get_map` пока уходят всем
- игрок-заглушка при старте больше не создаётся: его создаёт вход (`Engine.JoinPlayer`, `SpawnPlayer`)

## [0.1.0] - 2026-11-24
**Изменено**:
- глобальное переименование сущностей. изменён сеттинг
- модель времени и конкурентности зафиксирована: один актор симуляции + планировщик событий + акторы-сессии игроков, без тика (см. `documentation/architecture.md`, «Конкурентная модель»)
- тик симуляции 1 с заменён планировщиком событий: стройка, прибытие маршей и действия лагерей мародёров срабатывают по таймеру ближайшего события

**Технические детали**:
- в коде переименовали сущность `village` (деревня) в `settlement` (поселение)
- планировщик: `server/internal/sim/scheduler.go`, min-heap по `(fireUnix, seq)` в `World.Events`; `Engine.Advance(now)` и `Engine.NextEventUnix()` вместо `Engine.Tick`
- обработчик события получает игровым временем `fireUnix`, а не текущее время; после простоя сервера просроченные события применяются по порядку до приёма соединений
- отменённое событие из кучи не удаляется: `BuildJob`, `March` и `Camp` хранят `eventId` актуального события
- снапшот: убраны `tick` и `world.tick`, добавлены `world.events`, `world.eventSeq` и `eventId` у сущностей; версия формата осталась 1, снапшот без событий читается, события досоздаются из дедлайнов
- журнал боёв: поле `tick` заменено на `eventId` (событие прибытия марша)
- рассылка состояния всем раз в секунду пока осталась (отдельный `pushTick`), симуляцию она не двигает

**Исправлено**:

**Технические детали**:
- `clientState` в `state.go`: обёртка мира с состоянием деревни.
- `productionRate()`: базовое производство 10/час + бонусы зданий.
- `lastMapRequestAt`, `MAP_CACHE_TTL_MS`: кэширование запросов карты.
- `renderMap.lastRendered`: защита от повторной отрисовки тех же данных.

**Известные ограничения**:

**Технические детали**:

- `UpgradeBuilding` проверяет ресурсы, списывает, повышает уровень.

- `architecture.md`: обновлено описание Game Logic слоя, добавлена конкурентная модель (actor-модель, запрет глобального мьютекса, планировщик).

**Известные ограничения**:

## [0.0.2] - 2026-11-09

**Добавлено**:
- WebSocket-транспорт на `:8080/ws` — приём команд от клиентов, broadcast состояния всем подключённым.
- Очередь команд `chan Command` (буфер 100, FIFO) — WS-обработчик кладёт команды, главный цикл `main.go` забирает и исполняет.
- Debug HTML-клиент `client/index.html` — подключение по WebSocket, отображение состояния (ресурсы, здания, армия, тик), кнопки команд.
- Зависимость `gorilla/websocket v1.5.3` в `server/go.mod`.

**Технические детали**:
- Интерфейс `EngineInterface` удалён из `transport/ws.go` — сервер не трогает движок напрямую, только складывает команды в канал.
- Переполнение очереди: `select` с `default` — команда отклоняется с ошибкой `command queue full`, без блокировки.
- `BroadcastState(state)` рассылает состояние всем клиентам; мьютекс только на список клиентов, не на мир.
- Невалидные данные команды отклоняются сразу с поясняющей ошибкой клиенту.
- В `main.go` добавлен `case cmd := <-wsServer.CommandChan()` в главный `select` — вызов `executeCommand` только из этого цикла, движок потокобезопасно не трогается.
- `executeCommand` маршрутизирует `upgrade_building` / `train_unit` / `finish_now` с валидацией параметров; методы движка пока возвращают `not implemented` (заглушки).
- Клиент читает состояние из первой деревни: `resourcesMilli / 1000`, `buildings` как map ключ-уровень, `stationedInfantry`.
- HTTP-сервер запускается в горутине, не блокирует тик симуляции.

**Проверка**:
- `go build ./cmd/server` и `go vet ./...` — чисто.
- Тестовый WS-клиент подключился к `:8080/ws`, команды `upgrade_building` и `finish_now` дошли до главного цикла (в логе `command ... failed: not implemented` — заглушки работают).
- Состояние `{"type":"state","data":{"tick":19,...}}` приходит каждый тик всем подключённым.
- Переполнение очереди и невалидные данные возвращают `{"type":"error",...}` без блокировки.

**Известные ограничения**:
- Команды пока не выполняют реальных действий — нет методов в `sim.Engine` (заглушки).
- Начальное состояние приходит с первым тиком (в течение 1 сек после подключения).
- Broadcast шлёт весь `World` целиком (карта 100×100 на каждый тик) — для 1-10 игроков debug-режима приемлемо, при росте стоит слать снапшот только при изменениях или диффы.

## [0.0.1] - 2026-11-07

**Добавлено**:
- Проектный каркас: структура папок, конфиги (ресурсы, здания, юнит, бой), валидация конфигов при старте.
- Карта 100×100: генерация месторождений, размещение стартовой деревни игрока.
- Деревня: 6 зданий, 4 ресурса, производство по серверному времени.
- Войска: пехотинец, марши, провиант, отмена марша.
- Бой: формула атака/защита, модификаторы 1.5/3.0, потери.
- PvE: 5-10 статичных лагерей варваров, атака раз в 24 часа в окна игрока.
- Тестовый режим "завершить немедленно".
- Сохранение состояния: периодические JSON-снапшоты по `save-structure`.
- Headless-тесты логики (бой, производство, марши).

**Технические детали**:
- Engine не потокобезопасен: все вызовы только из одной горутины (актор мира с почтовым ящиком команд).
- Состояние только в памяти запрещено: снапшоты раз в N минут + журнал критичных событий.
- Глобальный мьютекс на мир запрещён как архитектурный костыль.

**Известные ограничения**:
- Нет клиентского транспорта — сервер headless, нечем играть.
- Нет аутентификации.
